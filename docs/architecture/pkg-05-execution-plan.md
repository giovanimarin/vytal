Estado: **planejado, pendente de aprovação**, 2026-11-05. Vinculado ao [ADR-0001](adr/0001-operational-persistence.md). Base `master` aaa66829642c2506b25634797687cc231a1984b3. Este PR entrega apenas estudo/decisão proposta; **não autoriza executar as tarefas de implementação abaixo**. Nenhum deploy, migração, apply, serviço pago, dado real ou alteração de repositório de dados nesta etapa.

## Limites e ordem

Preservar endpoints, payloads, status HTTP, identidade autenticada, resultados de readiness e comportamento legítimo Android/web. Aprovação de PostgreSQL não aprova serviço/topologia/custo automaticamente. Candidato preferencial é Cloud SQL em produção GCP; Neon é alternativa que requer aprovação explícita de fornecedor externo. SQLite segue local. BigQuery/GCS só entram depois da paridade operacional e aprovação de necessidade/custo.

Cada item vira PR pequeno com seus testes/evidências. “Independente” significa ter fronteira revisável e dependências explícitas, não que todas as tarefas possam ser implantadas isoladamente ou sem aprovação. Lotes de autenticação devem permanecer em uma fonte consistente; proibir feature flags que aceitem duas autoridades de sessão para a mesma conta.

## Contratos que precisam de proposta técnica antes do primeiro PR funcional

- Uma transação/unidade de trabalho usa **a mesma conexão** até commit/rollback, com pool limitado pelo orçamento de conexões do banco e máximo de instâncias/processos do servidor. Sem número fixo inventado: medir e documentar antes. Testar reuse de pool entre contas e cancelamento/timeouts.
- Toda escrita de domínio usa a conta obtida da autenticação validada, não user_id livre do cliente. Constraints reforçam integridade, não autorizam acesso. API v1 não expõe endpoint direto de banco/Data API nem credenciais de conexão.
- CAS de refresh precisa atomicidade no motor, hash único e verificação de expiração/revogação no mesmo comando/unidade. Falha/timeout de resultado pode deixar commit de estado desconhecido: definir política de reconciliação/relogin compatível, sem retry cego que produza outra sessão ou enfraqueça replay. Não mudar resposta v1 sem revisão.
- Chaves/nomes de campos, BOOLEAN vs inteiro, timestamps aware, DATE serializada, JSON e null exigem adapters explícitos; **não** trocar tipos públicos só porque PostgreSQL os representa melhor.
- PostgreSQL upsert não deve traduzir INSERT OR REPLACE por delete+insert. Campos de conflito/atualização e preservação de IDs devem ser especificados por tabela. Novo email case-insensitive, cascata destrutiva ou dedup por “mesmo dia” não são decisões já tomadas.
- Driver/ORM/migration tool e RLS ainda não escolhidos: propor a opção mínima que suporte transação/teste e evite SQL espalhado no HTTP. Não introduzir uma reescrita integral como pré-condição.

## Migração e rollback: critérios de passagem

| Gate | Evidência exigida | Quem aprova / ação se falhar |
| --- | --- | --- |
| G0 — ADR | Inventário, escolha de hospedagem condicional, comparação de custos e decisões AP-01–07 | PO/revisores; este PR permanece proposto |
| G1 — paridade local | Regressões existentes preservadas + PostgreSQL real, sem dados/cloud reais; API e clientes compatíveis; testes negativos/concorrência/rollback | Engenharia/revisor independente por PR; corrigir escopo antes de avançar |
| G2 — prontidão contratada | Cotação oficial, região/topologia, RPO/RTO/SLO, backup/restore, segurança/IAM/rede, limites e custo aprovados | PO/operação/segurança; não provisionar com lacunas |
| G3 — ensaio real autorizado | Autorização específica de dados/custo/acesso, backup consistente e restore provado, relatório de divergências, runbook de pausa/cutover/rollback | Responsáveis designados; falha mantém fonte antiga e produção bloqueada |
| G4 — cutover | Single writer, schema/API compatíveis, counts/referências/estado de sessão consistentes e smoke de cada conta | Nova aprovação operacional; **não concedida por este plano** |
| G5 — expansão analítica | Necessidade/custo/privacidade e replay/exclusão validados independentemente | Pode ser adiada sem impedir PG operacional |

Se houver escrita nova no PostgreSQL, não basta reverter a imagem para SQLite: o arquivo anterior estará atrasado e tokens podem ter sido consumidos. Definir checkpoint de corte, bloquear writer antigo e prever export/reconciliação consistente ou restauração autorizada com efeitos sobre sessões explicitamente avaliados. Não prometer downtime zero, rollback sem perda, RPO/RTO ou prazo de retenção que não foram acordados.

## Recomendações de sequência e revisão

Primeiro PR funcional futuro recomendado: **T01 + parte mínima de T03**, caracterização e testes PostgreSQL local descartável, sem alterar o provider de produção. O alvo é obter evidência do contrato de concorrência/constraints e revalidar o backlog no SHA real. T02 vem em PR separado pequeno. Autenticação só troca de fonte quando T05/T06 estiverem consistentes e revisados; não liberar isoladamente um hash/token writer em outro banco.

Depois de aprovar o ADR, engenharia pode propor detalhes técnicos rotineiros nos PRs; não precisa pedir decisão de produto para cada fixture ou nome de classe. Produto/operação ainda decide orçamento, residência/fornecedor, disponibilidade e janela de migração. Implementação, migração e deployment permanecem trabalhos distintos com autorizações próprias.
